# Reuse and generation

The home page reads "Find out ___ based on ___", and both blanks are free phrases: "which Disney princess you are" based on "your snack choices", or "where you should live" based on "your ideal weekend". The planner writes playable questions and choices first. The writer then illustrates them from a shared, searchable **asset library**. A cutout can serve as an answer in one quiz and a result in another.

A request runs in five steps:

1. **Check saved quizzes.** Quizzes saved before free-form wording keep their exact keys, so "which Disney princess you are" + "your favourite muffins" still opens the older "What Disney princess are you based on your favourite muffins?" quiz. Wording already matched to a saved topic alias ("princess from Disney") finds its older quiz too, with read-only lookups and no embedding. Older keys erased symbols, so wording containing them ("C++", "C#") skips this step. Newer keys, result names and refusal records spell symbols out in place, so "C#" matches "C sharp" but never "C++".
2. **Plan the quiz** (one text request per new wording). The planner chooses four real members of the requested outcome category, the relationship to the player, the angle of the questions, and the full questions, choices, and the score for each named result. It does this before it receives any pictures. The planner aims for short mobile copy and validates the finished text against storage limits so constrained generation cannot interrupt a choice at a character boundary. The server checks the choice counts and mappings and rejects duplicate choice sets. The category, relationship, question topic, angle, length and tone identify a saved quiz. Wording with the same planned meaning can reuse it. Finished quizzes from the earlier plan format remain accessible.
3. **Search the library.** Look up each portrait by normalized category and name first. An exact match works across embedding models and survives a failed vector search. The library can also offer same-name cutouts from other categories. The writer checks their depicted subjects, so a city can serve as a holiday destination and namesakes can be declined. A secondary semantic search can recover name matches from earlier, unindexed entries. The same embedding batch retrieves choice pictures, scenes and stickers. Scores are compared within an embedding model.
4. **Illustrate the planned quiz and write its results** (one text request). The writer gets the fixed choices, scoring and library descriptions. It supplies artwork and notes for each slot by ID. The server always takes the question text, answer text and votes from the plan. A hero can use a saved picture of a neutral subject named in the setup. The writer can use subject-specific library images, request missing cutouts, or select from the bundled sheet of generated editorial illustrations. Abstract choices can use these illustrations without an extra image request. The budget is **up to 12 new pictures per quiz, including portraits**, plus a separate background scene. A close match for the background setting reuses the saved scene even if the writer requests different lighting or props. The server validates the draft before paying for pictures.
5. **Draw only what is missing**, then lay out saved pixels for the player. Result portraits, other pictures and the scene are separate requests. Image providers refuse some named characters, and a refused portrait sheet must never blank the answers too. Refused or empty cells use the bundled illustrations. Refused results are remembered by image model, category and name, so later quizzes can use an illustrated award without another portrait request. Because a refused sheet can't say which subject caused it, a name counts as refused when it was alone on the sheet or after two refusals. A refusal is recorded at most once per quiz attempt, even across retries. Pictures that did draw are embedded and added to the library. The server then crops library cells, from any number of source atlases, into the player's existing two-by-two result atlas and five-column question atlas.

Both text sets still map to four shared personality archetypes: curious, bold, warm and driven. The planner assigns each named outcome its archetype and fixes result order before artwork is selected. `npm run library:index` indexes existing sprites by name and by category with name without embedding them again, then adds eligible cutouts from previously unindexed packed sets. Older opaque atlases are skipped because their cells carry a painted background.

Generation streams six steps to the page: checking saved quizzes, planning questions and choices, finding existing artwork, matching pictures and writing results, drawing missing artwork, and getting the quiz ready. The generation panel appears only after the server confirms it is creating something. Cache lookups and saved quizzes keep the home layout steady, with a busy button until their artwork is loaded. Steps that weren't needed are marked "Saved". Detailed progress requires `X-Quiz-Progress-Version: 2`. Other clients receive only the completion and error events, which all versions understand.

After the player answers, the reusable outcome introduction appears immediately. The answer-specific reading is generated separately from the saved quiz and the actual selected answers. The server supplies the exact choice quoted in the reading. That reading is cached by quiz UUID and ordered answer IDs. Share links contain only the quiz UUID, so recipients start with no answers selected.

## Spending controls

There is no daily cap on generation; Convex counts attempts and AI requests per UTC day for visibility. Understanding a new wording, creating a new quiz and a new personal reading each count as one attempt. An attempt is counted on its first paid request rather than when it is claimed, so a retry that only needs local composition is free. A brand-new idea therefore uses two attempts, a rewording of an existing idea one, and an exact repeat none.

Paid calls and the daily counters update in one transaction. A lease prevents concurrent Vercel instances from paying for the same plan or quiz. A quiz attempt can issue at most one writing request, one result-portrait sheet, one picture sheet and one scene, each recorded before contacting the provider. Local composition never increments image counters. The written draft is checkpointed before drawing. Each drawing request saves its own atlas and is checkpointed as soon as it settles, including when it was refused or failed, so a retry after one request fails only repeats that request. Failed attempts remain counted, and automatic SDK retries and provider fallbacks are disabled. Leases expire after five minutes if a process is lost.

Plans are capped at 5,200 output tokens, quiz writing at 9,000 and personal readings at 1,800. Sheets use medium-quality transparent cutouts. These are request/token limits, not a dollar budget; provider pricing still applies.

The saved result introduction and artwork remain visible even if a new personal reading cannot be made.

## Storage and access

Convex stores content sets, complete quizzes, artwork files, generation claims, and daily call counters. All library functions require a server-only random secret shared by Convex and the Next.js API. AI credentials and the Convex deployment key never reach the browser. Saved asset URLs use opaque UUIDs and are immutable.

Library pictures are drawn as transparent cutouts in up to four columns, using a native image endpoint with real alpha. Image models never draw an exact grid, so the server repacks each sheet: it finds objects by alpha, assigns them to their intended cells, and centres them with transparent padding in exact 512px cells. Ambiguous connected shapes that would need slicing leave their cells empty. Matching cut edges on adjacent packed cells with a separate object in one of them also disqualify both cells. The same check filters older packed sets during indexing. A library entry points to one source cell. Each request saves its own atlas, and a drawn scene is a one-cell atlas. In the composed question atlas the opaque scene occupies the start of an extra final row. Packed atlases are marked `packed`. Older opaque atlases still have each cell's outer 6.5% trimmed in the player. New quizzes bake generated illustrations into every visible question, answer and result cell. The player and share cards use the same bundled artwork for older saved quizzes with an `imageless` flag or no atlas.

The connected-background matte remover remains for compatibility with older foreground images. Existing local quiz assets can still be migrated without AI calls; a saved question still-life becomes the result background for migrated question sets.

The app retains legacy compressed quiz links for playback. The old local filesystem store is used only by the migration script and related compatibility tests. Production storage is Convex, so Vercel does not need a writable persistent filesystem.

## Per-quiz style

Each quiz carries an optional `style`, so no two look alike, without extra AI requests:

- **Palette.** When a quiz is assembled, the server reads its question set's background scene (and, for packed atlases, the cutouts above it) and derives colours in OKLCH: a soft tint of the scene's main hue for the page, ink adjusted to at least 7:1 contrast, and the most vivid distinct hue for the accent. Dark scenes get a dark page. It is pure image maths, so new pairings of old sets get a palette too.
- **Typeface.** The plan chooses one heading face from the curated list (`typefaces` in `src/lib/quiz.ts`). The browser loads only that font from Google Fonts before showing the quiz, giving up after 1.5 seconds.
- **Stickers.** The writer can select up to four stickers that fit the setting, including zero. Local composition places them after the result background in the quiz atlas. Existing placements, floating stickers, and reduced-motion behavior remain unchanged.

Quizzes saved before this have no `style` and keep their preset theme and the default heading font.

## Sharing results

"Share my result" shares `/?quiz=<id>&got=<resultId>`. The link still opens the quiz unanswered; `got` only chooses the link preview. The home page's `generateMetadata` points Open Graph and Twitter tags at `/api/quizzes/<id>/card?result=<resultId>`, a 1200×630 PNG drawn with `next/og`: the result portrait on the quiz's scene, in its palette, heading typeface and stickers. Phones that can share files attach the card image itself.

## Suggesting existing ideas

`/api/suggestions` groups the phrases of saved quizzes (`api.topics.savedQuizTopics`, cached for a minute). Older bare categories are shown as phrases ("which dog breed you are", "your favourite tea"), which still reach their saved quizzes. The home page shows up to four matches for the focused blank, ranking phrases paired with the other blank first. On keyboard/mouse devices, Tab or → accepts the best prefix completion in its saved casing.
